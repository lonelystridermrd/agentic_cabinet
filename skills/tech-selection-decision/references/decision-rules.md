# 裁决规则与冲突矩阵

> 决策不是加权求和，是**按顺序否决 + 在剩余项里取舍**。
> 下面的规则按优先级排列，前面的规则可以推翻后面的。

## 一、裁决顺序（R1 → R8）

**R1 需求优先于技术。**
任何"技术上更优"但不符合现实需求的选项，直接出局。判据：说不清它解决哪个场景的问题，就不选。

**R2 红线一票否决。**
无维护 / 不兼容目标内核 / 许可证不可接受 / 核心路径依赖外部服务 → 出局，不参与打分。

**R3 满载不达标 → 否决。**
最坏场景崩溃或超预算，其他维度再好也不选。**例外**：有明确的降级/限流方案且能把最坏场景拉回预算内，此时按"带条件的候选"处理，并写清条件。

**R4 典型场景必须达标。**
日常业务不达标，等于不可用。

**R5 轻载不作为优化目标。**
不为"空闲时更省"牺牲典型/满载表现（除非设备是电池供电且空闲占 90% 时间）。

**R6 预算内优先解耦与简单。**
性能都达标时，选依赖更少、接口更薄、替换成本更低的那个。**不要把"性能余量"花在复杂架构上。**

**R7 扩展性只覆盖可预期规模。**
默认 3 年、4× 规模；超出部分写进"未来重估条件"，不在本次买单。

**R8 新技术只在现有撞墙时采用。**
"更先进"不是理由；"现有方案在满载场景撞墙且新方案能解决"才是。

## 二、常见冲突与裁决

| 冲突 | 典型场景 | 裁决 |
|---|---|---|
| 性能 vs 解耦 | 自研可省 10%，但绑死内部接口 | 预算内选解耦；超出预算才选性能，并限定在单模块内 |
| 成熟 vs 先进 | 老库稳但无新特性 | 老库优先；新特性用旁路补齐，不整体替换 |
| 内存 vs 延迟 | 预分配省延迟但吃内存 | 先定内存上限；上限内预分配，超限用池+降级 |
| 兼容 vs 性能 | 新内核特性 vs 老设备 | 以最低支持内核为准；新特性做运行期探测降级 |
| 扩展 vs 简单 | 多线程模型 vs 单线程 | 不赌未来规模；单线程够用就不上多线程，留接口 |
| 自研 vs 引入 | 自研可控但担风险 | 引入成熟库为主；自研仅限"库解决不了且核心竞争点" |

## 三、否决清单（写进决策正文）

- 满载崩溃/超预算且无降级方案
- 停止维护 / 单人项目 / 高危漏洞未修
- 目标内核/架构不支持且无 backport 路径
- 许可证与交付方式冲突
- 不可回退且无回退计划
- 依赖外部服务在核心路径

## 四、置信度映射

| 条件 | 置信度 |
|---|---|
| 关键结论有实测 + 独立复核 + 满载推演 | `high` |
| 有官方文档/源码支撑，但性能靠报告或推算 | `medium` |
| 报告数据未实测，且无法独立验证 | `low`（写清缺什么） |

> 性能类结论默认最高 `medium`，除非有本平台实测。

## 五、报告采信规则

1. 报告是**输入**，不是证据。关键结论必须能追到原始来源（规范/源码/实测）。
2. 同一厂商多个页面 = 1 个来源。
3. "未实测"的数据一律按假设处理，并写"若假设不成立，结论如何变"。
4. 报告内部矛盾的结论，标"需验证"并优先复核。
5. 复核结论与报告不一致时，**以复核为准**，并在决策中记录差异。

## 六、决策正文必须包含

- 需求锚点（四场景数字）
- 否决项与依据
- 取舍点（放弃什么、为什么可以放弃）
- 反转条件（可观测）
- 迁移与回退成本
- 置信度与理由
