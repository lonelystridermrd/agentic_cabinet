# spec-writer — 需求规格

## 触发条件

- 需求只有一句话或一堆形容词，无法判断「做完没有」
- 要跨人/跨会话交接，必须先固定输入输出
- 实现前需要先对齐边界（改哪里、不改哪里）

**不触发**：已有明确验收标准的单步修改；纯技术选型（走 `decision-logger`）；纯排期（走 `task-tracker`）。

## 输入

- 需求原文（用户原话，不改写）
- 现状：涉及的文件/接口/数据表，用 `read`/`grep` 核实后的路径
- 约束：截止时间、不能动的东西、依赖方
- 历史：`python .dsh/tools/kb.py search <关键词> --limit 5` 的命中结果

## 步骤

1. **查先例**：`python .dsh/tools/kb.py search <关键词> --type decision --limit 5`，再跑一次 `--type experience`。
   **完成判据**：正文引用 ≥1 条 `dec-*`/`exp-*` 并说明相关性；没有就写「库内无先例」。
2. **复述需求**：用一句话写「谁在什么场景下要什么」，列出 2–3 条你自己补的假设。
   **完成判据**：用户确认这句话，或假设清单被逐条标为「确认/待确认」。
3. **写目标**：≤3 条，每条以动词开头且能验证。
   **完成判据**：每条目标都能回答「怎么测量」；答不出的删掉。
4. **写非目标**：≥2 条「本次明确不做」，每条给出不做的理由（范围/依赖/风险）。
   **完成判据**：非目标能挡住至少一个合理的追加需求。
5. **写接口契约**：对每个对外入口列输入字段、类型、可空性、输出形状、错误码与边界值。
   **完成判据**：字段名/类型/错误行为三项齐全；缺一项即未完成。
6. **写验收标准**：用 `给定…当…则…` 或可执行 checklist，每条对应一条命令或一个人工步骤。
   **完成判据**：每条验收都能被第三个人独立执行并判 通过/不通过。
7. **写风险**：≥3 条，每条含「触发条件 / 影响 / 缓解 / 回退」。
   **完成判据**：至少 1 条风险带可执行的回退动作。
8. **落盘**：已有任务卡则在其正文追加 `## 规格` 五段；无任务卡则交付正文，并建议用 `task-tracker` 建卡承载。
   **完成判据**：输出路径存在且五段标题齐全；`python .dsh/tools/kb.py validate` 零 error。

## 质量闸门

- [ ] 目标 ≤3 条，每条可测量
- [ ] 非目标 ≥2 条且写了理由
- [ ] 接口契约含字段名、类型、可空性、错误行为
- [ ] 验收标准每条可被第三人执行
- [ ] 风险 ≥3 条，至少 1 条带回退动作
- [ ] 全文 0 处实现细节（不写类名、算法、伪代码）
- [ ] 引用的 `dec-*`/`exp-*` 真实存在
- [ ] `kb.py validate` 零 error

## 输出格式

```
规格：<路径 或 "对话正文">
目标：1) … 2) …
非目标：1) …（理由）
接口契约：<入口> · 输入 … · 输出 … · 错误 …
验收：1) 给定…当…则…（证据：<命令/路径>）
风险：1) <触发> → <影响> → <缓解> → <回退>
待确认：<≤3 条，需用户拍板>
```

## 反面清单

- ❌ 把实现方案写进规格（选型、类图、伪代码）——那是下一步，不是契约。
- ❌ 目标写成「优化体验」「提升质量」——无法判定，等于没写。
- ❌ 验收写「功能正常」——没有执行主体与判据。
- ❌ 非目标留空——不做边界声明，范围必然膨胀。
- ❌ 替用户补需求却不标假设——把猜测当事实。

## 用例

**成功用例**：用户说「给知识库加个导出功能」。先 `kb.py search 导出` 确认无先例；复述「把指定 tag 的条目导成 markdown 包」；目标 2 条、非目标 2 条、契约含 `--tag`/`--out`/空结果行为；验收 3 条各带命令；风险 3 条含「导出中断→保留临时目录可续跑」。

**边界用例**：用户说「把这个按钮改成蓝色」。一句话可判定、无接口变化 → 判定不触发本 Skill，直接确认色值与验收（截图对比）后执行；若强行写五段规格，属于用流程替代判断。
