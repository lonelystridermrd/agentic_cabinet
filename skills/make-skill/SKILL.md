# make-skill — 元技能

## 触发条件

- 同样的话贴过 3 次（判据：能指出前两次发生在哪个任务）
- 用户明确要求「做成 Skill / 固化 / 标准化」
- 某个流程每次都要重讲，且步骤 ≥4 步

**不触发**：只出现 1 次的新做法（先记 TODO）、纯个人偏好、一次性脚本。

## 三问闸门（全过才写）

1. 有**单一清晰的触发条件**吗？（一句话能说完 → 没有就别写）
2. 不用它时，模型是不是**总在即兴发挥同一件事**？（不是就不值得抽象）
3. 权限边界能**一句话说清**吗？（说不清就还没想明白）

任一不过 → 输出「不建议抽象 + 理由」，停在讨论，不落盘。

## 形态判定树

```
需要「调真实系统」（读文件/跑命令/调 API）？
├─ 是 → Tool / Plugin（TS，Cordis 插件，需重启或热载）
└─ 否 → 需要「独立上下文 + 受限权限」且会产出大段中间结果？
        ├─ 是 → Subagent（写 .dsh/agents/<name>.md persona 卡片）
        └─ 否 → 每次会话都必须知道，且 ≤1 句？
                ├─ 是 → Instruction（AGENTS.md，注意 ≤12 条上限）
                └─ 否 → Skill（.dsh/skills/<name>/SKILL.md）✅ 本技能产出
```

判据表（选错形态的典型症状）：

| 形态 | 选对的信号 | 选错的信号 |
|---|---|---|
| Skill | 有明确 whenToUse，模型读完就知道怎么做 | 里面写满「调用某工具」的实现细节 |
| Agent | 需要只读探索/审计，产出可以丢回主会话 | 子 Agent 反过来频繁要求写权限 |
| Tool | 需要确定性的执行与回传 | 用 Skill 描述「如何执行命令」，每次还不一样 |
| Instruction | 违反一次就污染全局 | 写了 30 行步骤（该下沉） |

## 步骤

1. **查重**：`python .dsh/tools/kb.py search <关键词>`；已有同主题 Skill 则改旧的，不新建。
2. **命名**：kebab-case，`^[a-z0-9]+(-[a-z0-9]+)*$`，与目录同名，否则 DSH 静默跳过。
3. **生成草稿**（沙箱，G3）：
   ```
   .dsh/drafts/skills/<name>/SKILL.md
   ```
   不写进 `.dsh/skills/` —— 该目录会被 DSH 立即装载。
4. **front-matter 四件套**：`name` / `description`（≤80 字，写「做什么 + 适用什么说法」）/ `whenToUse`（触发条件，写用户会说的话）/ 可选 `metadata`。
5. **正文六段**：`## 触发条件` `## 输入` `## 步骤` `## 质量闸门` `## 输出格式` `## 反面清单`；复杂 Skill 再加 `references/`。
6. **写用例**：至少 1 个成功用例 + 1 个边界用例（触发但不适用 / 近似但不触发），写在 `## 用例`。
7. **自检**：`python .dsh/tools/kb.py validate`（会校验 name、description、whenToUse、≤8192 字节）。
8. **交付确认**：给出草稿路径 + 3 行摘要 + 「确认入库？」；用户 yes 后执行 `python .dsh/tools/kb.py promote .dsh/drafts/skills/<name>`。

## SKILL.md 骨架

```markdown
---
name: <kebab-case>
description: <做什么 + 适用什么说法，≤80 字>
whenToUse: <用户会说的触发语句，用引号列举>
---

# <标题> — <一句话定位>

## 触发条件
## 输入
## 步骤        （编号，每步都有可判定的完成判据）
## 质量闸门    （checkbox，不合格就退回）
## 输出格式    （模型该回什么）
## 反面清单    （❌ 典型错误做法）
## 用例        （1 成功 + 1 边界）
```

## 质量闸门

- [ ] 三问全过，且能指出「前 2 次重复发生在哪」
- [ ] `name` 与目录同名、kebab-case
- [ ] `whenToUse` 写的是**用户会说的话**，不是内部术语
- [ ] 步骤每步都有完成判据，无「适当处理」这类空话
- [ ] 权限边界一句话可述（能写哪里/不能写哪里）
- [ ] 正文 <8192 字节（DSH 工具结果修剪阈值）
- [ ] 有 1 成功 + 1 边界用例
- [ ] 草稿只落在 `.dsh/drafts/skills/`

## 输出格式

```
草稿已生成：.dsh/drafts/skills/<name>/SKILL.md（<字节数>）
触发：<whenToUse>
边界：能写 <...>；不能写 <...>
用例：成功 1 / 边界 1
入库命令：python .dsh/tools/kb.py promote .dsh/drafts/skills/<name>
待确认：yes / no / 改哪一句？
```

## 反面清单

- ❌ 直接写进 `.dsh/skills/`（绕过 G3 闸门，污染会话目录）
- ❌ 生成一堆触发条件重叠的 Skill（先查重，能合并就合并）
- ❌ 在 Skill 里写实现细节（那该是 Tool）
- ❌ `whenToUse` 写成「当需要时」（等于没有触发条件）
- ❌ 没有边界用例 —— 边界用例才是验证触发条件是否够窄的唯一手段

## 用例

**成功用例**：输入「我每周五都要手动汇总这周的决策和经验，太烦了」→ 判定为 Skill（有固定触发=周五、步骤可复用、无外部系统调用）→ 产出 `weekly-review` 草稿，含 whenToUse「说周报/本周总结」与 6 步流程。

**边界用例**：输入「帮我写个脚本把这堆 md 转成 pdf」→ 需要「调真实系统」（LibreOffice/脚本），判定为 **Tool/命令**而非 Skill；输出「建议用现有 office-export-pdf 能力 + 一条命令，不要新建 Skill」，并说明理由。
