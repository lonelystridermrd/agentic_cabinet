# release-manager — 发布管理

## 触发条件

- 一批变更要形成可识别的版本（tag/包/部署）
- 需要对外说明「这版有什么」
- 需要回滚预案才能上线

**不触发**：单文件热修且不产生版本（走普通提交）；内部实验分支；没有发布动作的日常合并。

## 输入

- 上次发布点：tag 或 commit
- 本次范围：`git log <last-tag>..HEAD`、`git diff --stat <last-tag>..HEAD`
- 发布环境与窗口、通知对象
- 数据库/配置/依赖是否有破坏性变更

## 步骤

1. **定范围**：`git log --oneline <last-tag>..HEAD` 与 `git diff --stat <last-tag>..HEAD`；无 git 时按用户给的变更清单或上次 CHANGELOG 列项。
   **完成判据**：每个 commit 映射到一条变更项；未映射的单独列出并说明原因。
2. **分类变更**：`feat`/`fix`/`refactor`/`docs`/`chore`/`breaking`，并标影响面（用户可见/内部）。
   **完成判据**：每条变更恰有一个类型；`breaking` 全部标出。
3. **定版本号**：按语义化版本——`breaking` → MAJOR，`feat` → MINOR，仅 `fix`/`chore` → PATCH。
   **完成判据**：版本号变化能用一条规则解释；与上次 tag 可比。
4. **写 changelog**：按类型分组，用户视角一句话 + 关联 `TASK-*`/`dec-*`。
   **完成判据**：每条有 ID 或显式写「无关联」；无内部黑话与未脱敏信息。
5. **过发布检查表**：构建、测试、迁移、配置、兼容性、监控、通知逐项 yes/no + 证据。
   **完成判据**：全 yes 才可发布；任一 no 即阻断并写恢复条件。
6. **写回滚预案**：触发条件 + 命令级回滚步骤 + 数据可逆性 + 回滚后验证指标。
   **完成判据**：回滚步骤可被第二人照做；未演练的必须标「未演练」。
7. **人工闸门**：对外发布/不可逆操作前停下，向用户出示清单与回滚预案，取得明确确认（AGENTS 12）。
   **完成判据**：有用户确认原文；未确认时只交付清单，不执行发布。

## 质量闸门

- [ ] 每个 commit 有归属，无「其他改动」
- [ ] 版本号符合 semver 规则，理由一句话
- [ ] changelog 按类型分组，每条有 ID
- [ ] 检查表每项有证据（命令输出/链接/路径）
- [ ] 回滚步骤到命令级，且标注是否演练
- [ ] 发布前已获用户明确确认
- [ ] 未把秘钥/内部域名写进 changelog（G5）

## 输出格式

```
版本：v<X.Y.Z>（<last-tag> → HEAD，<n> commits）
变更：
- feat: …（TASK-…）
- fix: …（无关联）
- breaking: …（dec-…）
检查表：构建 ✓ / 测试 ✓ / 迁移 ✓ / 配置 ✓ / 兼容 ✓ / 监控 ✓ / 通知 ✓
回滚：触发 <…> → <命令> → 验证 <指标>（已演练/未演练）
状态：已发布 / 仅出清单待确认
```

## 反面清单

- ❌ 没有 changelog 直接发版——使用者不知道改了什么。
- ❌ 版本号拍脑袋（加了功能却只升 PATCH）——依赖方会静默拿到破坏性变更。
- ❌ 回滚写「重新部署旧版」——没有命令与验证，等于没有预案。
- ❌ 检查表凭印象打勾——每项必须有证据。
- ❌ 未经用户确认就对外发布——违反 AGENTS 第 12 条。

## 用例

**成功用例**：用户说「准备发 1.2」。`git log v1.1.0..HEAD` 得 12 个 commit；1 个 breaking、4 个 feat、7 个 fix → 定 v2.0.0；changelog 分组并关联 TASK；检查表 7 项全 yes；回滚预案含迁移回退命令；用户确认后发布并记时间线。

**边界用例**：用户说「把 README 错字改一下，顺便发版」。改动仅 docs → 不生成新版本，直接提交并说明「文档修正不占版本号」；若用户坚持发版，则按 PATCH 出最小 changelog，仍要过检查表。
