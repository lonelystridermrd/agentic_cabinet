# 四场景建模

> 目的：把"高性能"翻译成四行数字。**没有满载场景的选型，等于没做选型。**

## 统一参数（每档都要填）

| 参数 | 含义 | 例 |
|---|---|---|
| 连接/会话数 | 同时在线 | 5,000 |
| 新建速率 | 每秒新建 | 200/s |
| 消息/包速率 | pps 或 msg/s | 200,000 pps |
| 消息大小 | 均值 / P99 | 128B / 1500B |
| 并发线程 | 工作线程数 | 8 |
| 内存上限 | 进程 RSS 预算 | 64 MB |
| 延迟目标 | P50 / P99 / 最大 | 0.5 / 2 / 10 ms |

## 四档定义

| 档位 | 负载 | 目的 | 通过标准 |
|---|---|---|---|
| 理想轻载 | 容量的 10% | 验证功能与基线开销 | 无异常；空闲 CPU 低；无轮询空转 |
| 典型场景 | 容量的 40–60% | 日常业务 | P99 达标；RSS 在预算内；无持续队列增长 |
| 重载 | 容量的 80% | 接近拐点 | P99 不超过目标的 1.5 倍；无错误率上升 |
| 满载最坏 | 100% + 峰值突发 + 故障注入 | 找崩溃点 | **不崩、不雪崩、可恢复**；延迟可退化但不能失控 |

## 故障注入（满载档必做）

- 单连接异常（半开、重置、慢速读）
- 依赖抖动（磁盘慢、DNS 超时）——若存在
- 内存紧张（接近上限）
- 单核被抢占（模拟中断风暴）
- 优雅退出（有长连接时能否在 N 秒内退出）

## 退化曲线（写进决策）

对每个候选，回答：
1. 从典型到满载，哪个指标先崩（延迟 / 内存 / CPU / 错误率）？
2. 崩塌是**线性的**还是**悬崖式**的？悬崖点在哪？
3. 崩塌后能否自愈（降级、丢弃、限流），还是直接不可用？

## 从模糊需求推数字（用户只给形容词时）

| 用户说 | 先问 | 兜底默认（需标注"假设"） |
|---|---|---|
| "高并发" | 连接数上限？新建速率？ | 5k 连接 / 200 新建/s |
| "低延迟" | P50 还是 P99？多少 ms？ | P99 ≤ 2ms |
| "内存要小" | 进程预算多少 MB？每连接可接受多少？ | 64MB / 每连接 ≤8KB |
| "要能扩展" | 几年内、几倍规模？ | 3 年 4× |

兜底值只能用于**初筛**，进入决策前必须由用户确认或标注为"假设"。

## 输出模板

| 场景 | 连接 | 新建/s | pps | 延迟 P99 | RSS | 结论 |
|---|---|---|---|---|---|---|
| 轻载 | 500 | 20 | 20k | — | — | 通过 |
| 典型 | 3,000 | 120 | 120k | 1.8ms | 48MB | 通过 |
| 重载 | 4,000 | 160 | 160k | 3.1ms | 61MB | 接近预算 |
| 满载 | 5,000 | 200 | 200k | **8.4ms** | 72MB | **超预算 → 否决** |
