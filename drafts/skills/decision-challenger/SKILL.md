# decision-challenger — 决策压力测试

## 触发条件

- `dec-*` 即将从 `proposed` 转为 `accepted`，且 `confidence` 不是 `high`
- 决策不可逆或迁移成本高（涉及数据格式、目录结构、对外接口）
- 用户主动要求找反例

**不触发**：纯执行类小决策（可随时回退）、已有实测支撑的 `high` 决策。

## 输入

- 决策条目全文（front-matter + 三段正文）
- 当时的约束条件（时间/人力/合规）

## 步骤

1. **读决策**：取 `rationale` 与 `consequences`，标出「最弱的一环」（通常是唯一支撑理由）。
2. **Pre-mortem**：假设 3 个月后它失败了，列出 3 个最可能的失败路径，每条给触发条件与早期信号。
3. **反证**：为每个备选方案说一句「它其实更好的场景」，检查是否被过早否决。
4. **冲突检查**：`python .dsh/tools/kb.py search <关键词> --type decision`，找相冲突的旧决策 ID。
5. **结论**：维持 / 降级为 `low` / 改为 `proposed` / 加一条「回退触发条件」。只给建议，不改条目。
6. **回执**：输出结论 + 建议写入 `## 可信度压力测试` 的 3 行；由用户决定是否落库。

## 输出格式

```
结论：维持 accepted | 建议降级 | 建议加回退条件
最弱一环：<rationale 中唯一支撑点>
失败路径
1. … 早期信号：…
2. …
3. …
过早否决的备选：<方案> 在 <场景> 下更优
冲突决策：dec-…（是否构成冲突：是/否）
建议追加到条目：<3 行文本>
```

## 质量闸门

- [ ] 3 条失败路径都带「早期信号」（可观测，不是"可能会失败"）
- [ ] 至少检查 1 条备选是否被过早否决
- [ ] 冲突检查已跑，结论明确
- [ ] 只给建议，未擅自改条目

## 反面清单

- ❌ 泛泛说"有风险"——必须给触发条件与信号
- ❌ 把 pre-mortem 变成否定一切——目标是提高可信度，不是推翻
- ❌ 直接改 `status` 字段——修改需用户确认
