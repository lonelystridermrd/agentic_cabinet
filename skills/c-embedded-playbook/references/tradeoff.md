# 空间与时间取舍（决策表）

> 嵌入式的核心矛盾：RAM 便宜但不无限，CPU 便宜但不可预测。
> 原则：**把取舍写下来，用数据支持，别靠感觉。**

## 1. 决策矩阵（按场景查）

| 场景 | 倾向方案 | 触发条件 | 反例/代价 |
|---|---|---|---|
| 高频小计算（CRC、校验、查表） | 查表 | 表 < 8KB 且命中率高 | 表大导致 cache miss，反而更慢 |
| 低频复杂计算 | 现算 | 调用频率 < 1/s | — |
| 配置/静态数据 | 预计算存内存 | 内存占用可接受 | 内存紧张时压缩存储、用时解压 |
| 大对象偶尔访问 | 压缩存储 + 按需解压 | 解压耗时 < 省下的 IO | 解压后要放得下 |
| 请求级临时对象 | arena 分配 | 生命周期一致 | 不能单独释放某个对象 |
| 长生命周期对象 | 固定池 | 数量有上限 | 上限估小会拒绝服务 |
| 频繁增删的集合 | 哈希/树 | 数量 >100 | 小集合用数组更快 |
| 只读小集合 | 有序数组 + 二分 | n < 1000 | 插入变成 O(n) |

## 2. 典型取舍对

### 内存换 CPU
- 缓存 DNS/路由/配置查询结果：省重复计算，代价是失效管理。
- 预展开数据结构（例如把配置树展开成数组）：省指针追逐，代价是加载时间与内存。
- **判据**：缓存命中率 >80% 且失效逻辑可证明正确，否则不要缓存。

### CPU 换内存
- 压缩（zlib/lz4）：省 50–70% 内存，代价是压缩解压 CPU。lz4 解压 ~1GB/s，通常可接受。
- 位图代替布尔数组：省 8×，代价是位运算与代码复杂度。
- 共享内存/写时复制：省重复数据，代价是同步与生命周期。

### 批量换延迟
- 攒批发送/落盘：吞吐上升，单条延迟上升。
- **判据**：延迟预算允许的最大攒批时间（如 1ms）；到时间或到条数就发。

### 并发换简单
- 单线程事件循环：无锁、可预测，但一个慢操作阻塞全部。
- **判据**：单次处理最坏耗时 × 事件率 < 1 才有余量。

## 3. 量化方法

1. 写出两个方案的内存公式：`N × (sizeof(obj) + overhead)`。
2. 写出延迟公式：`固定开销 + N × 单次开销`。
3. 用真实数据代入（峰值 N、最坏输入），而不是平均值。
4. 不确定的参数标"待测"，并写出测量方法。

## 4. 记录模板（落 `dec-*`）

```
背景：<为什么要选>
方案 A：<描述> — 内存 <x> KB，延迟 <y> us，复杂度 <低/中/高>
方案 B：<描述> — ...
选择：<A/B> — 关键理由（哪条约束起决定作用）
代价：<放弃了什么>
验证：<如何证明选对了>（压测/线上指标/回归）
置信度：<high/medium/low> + 理由
```

## 5. 反模式

- ❌ "先这样，性能不够再优化"——没有预算的"再优化"通常意味着重写。
- ❌ 用 64 位类型存小范围值（表项 100 万 × 8B = 8MB，用 uint16 只有 2MB）。
- ❌ 为了省 1KB 内存写出 200 行位操作代码（维护成本远超收益）。
- ❌ 缓存一切（失效逻辑的 bug 比性能问题更难查）。
- ❌ 只看内存总量不看碎片（运行 30 天后 malloc 失败才发现）。
