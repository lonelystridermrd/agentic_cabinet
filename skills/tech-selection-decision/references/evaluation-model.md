# 七维评估模型

> 每个维度必须有**判据**和**测法**；写不出测法的维度，说明还没想清，删掉。

## 1. 系统性能

| 子项 | 必答 | 测法/判据 |
|---|---|---|
| 执行效率 | 每条热路径多少 syscall、多少内存访问 | `strace -c`、`perf stat`、源码走读；每请求 syscall 数 |
| 内存开销 | 常驻、峰值、每连接增量 | `/usr/bin/time -v`、`ru_maxrss`、池水位 |
| 线程开销 | 线程数、栈大小、上下文切换 | `top -H`、`/proc/<pid>/status`、`perf sched` |
| 调度合理性 | 有无长阻塞点、优先级是否合理、能否绑核 | 阻塞调用清单、`pthread_setaffinity` 使用情况 |

**否决线（示例，按项目调）**：每连接内存 > 预算/最大连接数；热路径存在无界阻塞。

## 2. 数据结构合理性

| 子项 | 必答 |
|---|---|
| 存储量级 | 10 / 1k / 100k / 1M 条？单条多大？放大倍数？ |
| 增删改查 | 各操作复杂度；最频繁的是哪个 |
| 内存布局 | 指针追逐次数；cache line 命中；是否 SoA 更优 |
| 并发访问 | 单写多读？多写？需要什么同步原语 |

**判据**：能画出"最热操作"的访问路径（访问了几个节点、几次 cache miss 风险）。

## 3. 用户场景（四档，缺一不可）

见 `scenario-model.md`。核心判据：**满载不达标 = 一票否决**；典型不达标 = 否决。

## 4. 技术成熟度

| 子项 | 判据 |
|---|---|
| 生产年限 | ≥3 年且有公开生产案例 |
| 版本节奏 | 近 12 月有发布；无"两年无提交" |
| 缺陷 | 高危 CVE 有补丁；关键 issue 有响应 |
| 可维护性 | 团队能读懂核心源码；有文档/示例 |
| 供应链 | 许可证、维护者数量、是否有商业支持 |

**否决线**：停止维护 / 单人项目 / 高危漏洞长期未修。

## 5. 兼容性

| 子项 | 判据 |
|---|---|
| 内核 | 目标内核版本是否满足（功能矩阵） |
| libc | glibc / musl / uClibc 差异 |
| 架构 | arm64 / mips / x86 交叉编译可行性 |
| 构建 | Makefile/CMake/autotools，能否裁剪 |
| 接口 | 与现有模块的 ABI/API 兼容；升级是否破坏 |
| 升级路径 | 大版本迁移成本 |

**否决线**：目标内核/架构无法支持，且无 backport 方案。

## 6. 解耦原则

| 子项 | 判据 |
|---|---|
| 依赖方向 | 依赖是否单向；是否反向依赖业务 |
| 可替换性 | 替换该组件要改几处？接口是否稳定 |
| 边界 | 接口能否用 5 行描述清楚 |
| 构建期耦合 | 是否强制引入一堆无关依赖 |
| 运行期耦合 | 是否要求特定进程模型/线程模型 |
| 单点 | 该组件的失败是否导致全局不可用 |

**判据**：能否在不动业务代码的前提下替换实现。不能 → 解耦不足。

## 7. 可扩展性

| 子项 | 判据 |
|---|---|
| 水平 | 加核/加进程后吞吐是否线性；锁竞争点 |
| 垂直 | 新增功能是否要改核心 |
| 数据规模 | 10× 数据量时复杂度是否退化 |
| 协议/格式 | 新版本协议能否平滑扩展 |

**判据**：只评估**可预期规模**（默认 3 年），不做无限外推。

## 权重推导（不是拍脑袋）

1. 四场景里哪一档是业务生死线？（通常"满载"或"重载"）
2. 生死线场景最敏感的维度权重 ×2
3. 红线维度（兼容性/成熟度）先否决，不参与打分
4. 权重写进决策正文，后续复议时可直接复用
