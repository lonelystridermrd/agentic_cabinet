# 新增技术选型决策层：建议由技能形成，拍板由人确认

## 背景

当前链路已经有两段：

- `tech-evaluation`：广度发散 → 收敛 → 原理/演进/实测 → 决策材料（明确不决策）。
- `research-assistant` / `tech-investigator`：取证。

但"材料 → 决定"这一步仍然靠人临场判断。用户要求一个**资深、有独立思考**的决策者角色，显式纳入七个层面（系统性能、数据结构、用户场景、成熟度、兼容性、解耦、可扩展性），并且要对输入报告做来源与置信度审查、单点发散复核。

## 评估

| 方案 | 需求约束是否显式 | 满载否决 | 可追溯性 | 额外成本 |
|---|---|---|---|---|
| A 不做决策层 | 否 | 无 | 低（只在人脑里） | 0 |
| B 让 tech-evaluation 兼做 | 部分 | 容易被流程末端压缩 | 中 | 低 |
| C 只写检查清单 | 是 | 靠自觉 | 中 | 低 |
| D 新增决策 Skill | 是（四场景闸门） | 写成 R3 硬规则 | 高（dec 可回查） | 中 |

## 最终选择

选 D。`tech-selection-decision` 负责：

1. **需求闸门**：四场景数字缺失即停止，不做技术驱动决策。
2. **审报告**：抽检关键结论，标采信/存疑/需验证；未实测按假设处理。
3. **独立复核与单点发散**：至少 1 条复核、2 处单点替代评估。
4. **七维评估 + 场景推演**：满载不达标一票否决（R3）。
5. **冲突裁决**：性能 vs 解耦等，按 R1–R8 顺序。
6. **出建议**：首选/备选/否决/反转条件/回退成本，交 `decision-logger` 落 `proposed`。

## 后果与代价

- 决策前必须先有四个场景的数字，需求模糊时流程会"停下来问"，不能一键出结论。
- 决策可能与调研报告的条件映射不一致；必须在正文写"分歧点"，不允许静默覆盖。
- 报告未实测时，决策置信度最高只能 medium（性能类结论默认 medium）。
- 与 `decision-challenger` 串联后多一次往返：先决策，再 pre-mortem，最后 accepted。

## 置信度理由

medium：流程与规则可验证（R1–R8 可逐条检查），但首次真实决策尚未跑过；七维权重仍靠人给，模型可能把权重当装饰。
