# research-assistant — 技术调研

## 触发条件

- 要做技术选型，且候选 ≥2
- 需要外部事实（版本、性能、限制）而库内没有
- 结论会影响后续实现或成本

**不触发**：已有 `accepted` 决策且约束未变（直接引用）；纯执行任务；一句话可查的 API 用法。

## 输入

- 决策问题一句话（要定什么、为什么现在定）
- 评估维度 3–5 个，必须可比较
- 约束：时间、团队栈、合规、预算
- 库内先例：`python .dsh/tools/kb.py search <关键词> --limit 5`

## 步骤

1. **定问题与维度**：写一句话决策问题 + 3–5 个维度，每个维度能对两个方案比出高低。
   **完成判据**：维度表里没有「好/差/优雅」这类不可判定词。
2. **拆子问题**：拆成 2–5 个可独立回答的子问题，每个配 2–4 个检索词。
   **完成判据**：每个子问题都能用「是/否/数值/版本」回答。
3. **查内部先例**：`python .dsh/tools/kb.py search <关键词> --type decision --limit 5`。
   **完成判据**：引用 ≥1 条 `dec-*` 并说明是否仍适用；没有则写「库内无先例」。
4. **多源检索**：每个子问题 ≥2 个独立来源，至少 1 个一手来源（官方文档/源码/issue/基准测试）；记录 URL、访问日期、版本。
   **完成判据**：来源表每行可点开；二手来源未单独支撑任何结论。
5. **建对比矩阵**：方案 × 维度，每格填可验证值（版本号、依赖数、耗时、回滚步骤数）。
   **完成判据**：未知的格子写「未知 + 验证成本」，不留空、不写形容词。
6. **给推荐与不确定性**：首选 + 次选 + 反转条件（什么新信息会推翻结论）；置信度按 G4 取 `high|medium|low` 并写一句理由。
   **完成判据**：每个不确定性都有「如何证伪」；`low` 必须写清什么信息会推翻它。
7. **生成决策草稿**：`python .dsh/tools/kb.py new decision --title "<场景>" --slug <kebab-case>`，填 `decision` 一句话结论、`alternatives`/`rationale`/`consequences`、`tags` 2–6 个（先 `kb.py tags` 查重），保持 `status: proposed`，等用户拍板。
   **完成判据**：草稿路径存在；`kb.py validate` 零 error；未擅自改成 `accepted`。

## 质量闸门

- [ ] 每个结论都能追到来源 URL 或库内 ID
- [ ] 至少 1 个一手来源
- [ ] 对比矩阵无形容词、无空格子
- [ ] 引用的 `dec-*` 真实存在且说明了适用性
- [ ] 置信度与理由一致（G4）
- [ ] 草稿 `status: proposed`，拍板权留给用户
- [ ] 脱敏：无内部域名、无生产数据（G5）

## 输出格式

```
问题：<一句话> · 维度：<3–5 个>
先例：dec-…（仍适用/已过时）/ 库内无先例
矩阵：
| 方案 | 维度1 | 维度2 | 维度3 |
推荐：<首选>，次选 <…>
不确定性：1) …（证伪方式：…）
置信度：high|medium|low —— <一句理由>
草稿：<dec 路径>（status: proposed，待你拍板）
```

## 反面清单

- ❌ 只搜一次就下结论——单来源等于没验证。
- ❌ 把博客/二手文章当一手来源——版本与限制必须回官方文档核对。
- ❌ 堆一堆链接不给结论——调研的产出是判断，不是书签。
- ❌ 替用户把草稿改成 `accepted`——拍板是人的动作（AGENTS 12）。
- ❌ 矩阵里写「性能更好」——没有数值就不是对比。

## 用例

**成功用例**：用户问「索引要不要上向量检索」。维度定成本/召回/运维；3 个子问题；先例命中 `dec-2026-11-07-g6-index-strategy` 且仍适用（条目数远低于 200）；矩阵给扫描耗时与依赖数；推荐「暂不上，保留 tag 入口」，不确定性写「条目 >200 时重估」；落 `dec-*` 草稿 `proposed`。

**边界用例**：用户问「Python 怎么读 JSON」。单点事实、官方文档一处可答 → 不触发本 Skill，直接给 `json.load` 用法与文档链接；强行走七步调研属于过度流程。
