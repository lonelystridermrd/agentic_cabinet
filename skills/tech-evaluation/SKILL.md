# tech-evaluation — 技术调研编排（出材料，不做决策）

> **三层分工**：
> - **取证**：`research-assistant` / `tech-investigator` 找事实、给来源、出矩阵。
> - **编排（本 Skill）**：决定查什么、查到什么程度、怎么实测、如何组织成决策材料。
> - **决策**：人。本 Skill 不给"最终选哪个"，只给"若约束是 X，则 A 更合适"的**条件映射**。

## 触发条件

- 要引入/替换一项技术，影响 ≥6 个月
- 候选多、信息混乱，需要先广度后深度
- 需要可复现的实测数据（体积/内存/启动/依赖），不满足于二手 benchmark
- **不触发**：单点事实（查文档或派 `tech-investigator`）；已有 `accepted` 决策且约束未变；纯学习阅读

## 输入（五问）

1. **目标与成功标准**：可量化（延迟/吞吐/内存/交付期）
2. **硬约束**：平台、架构、编译器、许可证、体积上限
3. **红线**：默认两条——无维护项目、核心路径依赖外部服务（见 `references/preference-profile.md`）
4. **时间盒**：广度多久、深度多久
5. **实测条件**：能否编译运行；目标 arch / 工具链 / 编译选项；能否上真机

## 步骤

### A 广度（只发散，不筛选）

1. 列 **≥8 个候选**：主流 / 备选 / 已淘汰但值得参考 / 自研或裁剪 / 维持现状。每个一句"它解决哪类问题"。
2. 派 `tech-investigator` 并行取证（每路 2–4 个问题）：定位、维护状态、许可证、生态。
3. 出广度清单，只标注"明显撞红线"，**不在这一步淘汰**。

### B 收敛（按硬约束筛，需人确认）

4. 用硬约束 + 红线筛到 **2–4 个方向**；每个淘汰项写清"撞了哪条约束"。
5. 把收敛结果交用户确认——这是流程中**唯一必须停顿**的中间点。

### C 深度（原理 + 演进 + 实测）

6. 每个方向：**演进时间线**（谁提出 / 解决什么 / 被谁取代或吸收 / 当前处于上升·稳定·维护·退场）、**原理机制**（为什么能做到）、**失败模式**（什么条件下退化）。
7. **编译产物实测**：写最小可编译样例，测产物体积、运行时内存峰值、启动时间、依赖数量、编译时间。方法见 `references/measurement.md`，必须记录六要素。
8. **证据定级**：自测 = A；他人带方法的 benchmark = B；博客 = D。规则见 `references/evidence-grading.md`。
9. **交叉验证**：≥3 个成熟项目的实际用法与踩坑记录（issue/CVE/迁移史）。

### D 产出（决策材料，不是决策）

10. **条件映射表**：`若 <约束> → <方案>`，覆盖全部保留方向；**不给单一结论**。
11. 按 `references/report-template.md` 出报告，落 `.dsh/knowledge/reports/<date>-<slug>.md`。
12. 用户拍板之后，才由 `decision-logger` 写 `dec-*`；本 Skill **不写**决策条目。

## 质量闸门

- [ ] 广度 ≥8，含"维持现状"与"已淘汰但值得参考"
- [ ] 收敛 2–4 个，每个淘汰项写了撞哪条约束
- [ ] 每个方向有演进时间线 + 原理机制 + 失败模式
- [ ] 每个方向有实测数据，或明确写"未实测 + 原因 + 补齐成本"
- [ ] 实测记录架构/编译器版本/编译选项/链接方式，别人能复现
- [ ] 证据表齐全，D 级只作线索
- [ ] 条件映射表存在，且**没有**"最终推荐 / 建议选 X"
- [ ] 未知项与待测项列全

## 输出格式

```
范围：<问题> ｜ 硬约束：<…> ｜ 红线：<…>
广度：<n> 个（列出）
收敛：<2–4 个> ｜ 淘汰 <x> 个（各一句撞哪条约束）
实测：| 方案 | 体积 | 峰值内存 | 启动 | 依赖数 | 编译时间 |（附工具链与选项）
证据：A n / B m / C k / D j
条件映射：若 <约束> → <方案>；若 <约束> → <方案>
未知/待测：<…>
报告：<路径>
```

## 反面清单

- ❌ 给"最终选 A"——决策是人做的，越权即失效
- ❌ 广度不足就深入：漏掉整个方向时，后面的数据再准也没用
- ❌ 拿别人的 benchmark 当自己的数据；引用时必须标来源与测试条件
- ❌ 实测不写工具链/编译选项（`-Os` 与 `-O2`、静态与动态混着比 = 数据无效）
- ❌ 只比功能不比体积/内存/依赖——嵌入式里这些就是硬约束
- ❌ 收敛阶段偷偷把候选删到只剩自己看好的那个
- ❌ 把 D 级博客结论写进证据表

## 用例

**成功用例**：评估"嵌入式 MQTT 客户端库"。广度列 9 个（mosquitto / paho / 裁剪版 / 自研 / 维持现状…）；收敛 3 个（静态体积 <300KB、无外部服务依赖、维护活跃）；每个方向实测 `-Os` 静态产物体积、峰值 RSS、启动时间、依赖数、`-j1` 编译时间；演进说明 MQTT 5.0 特性覆盖差异；产出条件映射（"要 MQTT 5.0 → A；只需 3.1.1 且体积优先 → B"），不写"建议选 A"。

**边界用例**：问"epoll 支持哪些事件"。→ 单点事实，直接查 man page 给结论，不触发本 Skill 的广度/实测流程。
