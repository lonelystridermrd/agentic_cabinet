# incident-responder — 故障响应

## 触发条件

- 生产/共享环境出现影响用户的异常
- 异常在扩散，或原因不明且影响面无法估计
- 需要一份可复盘的时间线与根因

**不触发**：本地开发环境的一次性报错（走 `experience-capture`）；已知且已有 SOP 的例行重启；性能优化（走 `research-assistant` 或专项任务）。

## 输入

- 现象：报错原文（脱敏）、影响面、开始时间
- 可用手段：日志入口、监控面板、回滚/降级开关、值班人
- 最近变更：`git log --oneline -10`、发布记录、配置改动

## 步骤

1. **定级与止损**：先判断影响面（用户数/核心链路/数据）与是否扩大，再执行止损——回滚、降级、限流、关开关，四选一或组合。
   **完成判据**：止损动作有执行时间与前后指标对比；未止损前不进入根因分析。
2. **建时间线**：从发现开始逐条记录 `HH:MM 事件/动作/证据`，含发现、止损、恢复、验证四个节点。
   **完成判据**：时间戳单调递增；相邻空白 >30 分钟处必须补「当时在做什么」。
3. **列假设并验证**：≥3 个假设，每个配一条验证命令/日志查询与结论（证实/证伪）。
   **完成判据**：每个假设都有明确结论；禁止用「可能是网络问题」结案。
4. **定根因**：落到机制层——配置、代码缺陷、依赖版本、容量、权限。区分触发因素与根本原因。
   **完成判据**：能回答「为什么之前没发生」和「为什么没更早发现」；答不出说明根因没到底。
5. **验证恢复**：核心指标回到基线，并观察 ≥30 分钟。
   **完成判据**：给出恢复前后同一指标的数值对比，不是「看起来好了」。
6. **经验入库**：排查 >10 分钟即走 `experience-capture`，落 `exp-*` 且必须含一句可执行 `prevention`。
   **完成判据**：`python .dsh/tools/kb.py validate` 零 error；`python .dsh/tools/kb.py index` 已跑；`exp-*` 路径与 `prevention` 原句可引用。
7. **写复盘**：`## 时间线` `## 根因` `## 改进项`，改进项带负责人与截止日。
   **完成判据**：每条改进项有 owner + 日期 + 验收方式；无「加强监控」这类不可验收项。

## 质量闸门

- [ ] 止损发生在根因分析之前，且有指标证据
- [ ] 时间线有真实时间戳与证据来源
- [ ] 每个假设都被证实或证伪，无悬空
- [ ] 根因在机制层，能解释「为何现在发生」
- [ ] 恢复有前后指标对比与观察窗口
- [ ] `exp-*` 已入库且 `prevention` 可执行
- [ ] 日志/条目已脱敏：无 token、内部域名、真实数据（G5）

## 输出格式

```
影响：<范围> · 开始 <HH:MM> · 恢复 <HH:MM> · 持续 <n> 分钟
止损：<动作> @<HH:MM>，指标 <前> → <后>
根因：<机制级一句话>
时间线：<路径或表格>
改进项：
| # | 动作 | 负责人 | 截止 | 验收 |
经验：exp-YYYY-MM-DD-slug —— prevention：<原句>
```

## 反面清单

- ❌ 先分析根因再止损——影响面在扩大，分析越久损失越大。
- ❌ 根因写「网络抖动」「环境问题」——不是机制，无法预防。
- ❌ 时间线靠事后回忆、无时间戳——复盘无法定位决策延迟。
- ❌ 恢复就结案，不做经验入库——同类故障必然复发。
- ❌ 把生产日志原文贴进知识库——G5 直接拒收。

## 用例

**成功用例**：用户报「接口 500 激增」。先限流止损并记录指标；时间线 6 条；3 个假设逐一证伪，最终定位为配置项在新版本被覆盖；回滚配置后指标 12 分钟回基线；入库 `exp-*`，prevention 写「发布检查表必须 diff 配置默认值」；复盘 3 条改进项带 owner。

**边界用例**：用户说「我本地跑测试报了个错」。无用户影响、单机、可复现 → 不触发本 Skill，转 `experience-capture` 记录；把它当事故会挤占真实故障的响应带宽。
