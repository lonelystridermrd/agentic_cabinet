# code-reviewer — 只读代码审查

## 触发条件

- 有明确变更面：`git diff`、PR、或用户给的文件清单
- 合并/发布前的最后一道检查
- 需要独立视角判断安全、边界、资源与越权

**不触发**：需求是否合理（走 `spec-writer`）；代码风格与格式化（交给 formatter）；没有变更面的全仓通读。

## 输入

- 范围：`git diff --stat`、`git diff --name-only` 或文件清单
- 上下文：本次变更要解决的 TASK/dec（没有就问）
- 约束：不能执行的命令、敏感路径、只读要求

## 步骤

1. **定范围**：`git diff --stat`；需要逐行时 `git diff -- <file>`。无 git 时按用户清单。
   **完成判据**：写出「文件数 + 变更行数 + 未覆盖范围」；未覆盖范围不得为空。
2. **选执行者**：变更 ≤200 行且单文件 → 主会话按本流程自查；否则按 `agent-dispatch` 派 `code-reviewer` 子 Agent。
   **完成判据**：派发 prompt 含六段（角色/任务/输入/权限/知识库/输出），并写死「read-only，不得写任何文件」。
3. **分级**：每条问题归入且仅归入一级——P0 阻断（错误/安全/数据丢失）、P1 高（逻辑缺陷/资源泄漏）、P2 中（可维护性）、P3 低（风格）。
   **完成判据**：能对每条复述分级依据；同级内按影响面排序。
4. **取证**：每条给 `文件:行` + ≤3 行证据 + 最小修复方向 + 是否阻断；不确定的标「待确认 + 需要什么信息」。
   **完成判据**：零条问题缺 `文件:行`；零处使用「可能/大概」下结论。
5. **敏感信息**：发现 token/密码/私钥/内部域名 → 立即停止，标 `P0 安全`，不复述原文（G5）。
   **完成判据**：报告、日志、调用记录中检索不到秘钥原文。
6. **出结论**：可合并 / 需修改 / 需重做，并给最大单点风险。
   **完成判据**：存在 P0 或 P1 阻断时结论不得为「可合并」；结论与阻断计数一致。
7. **记日志**：`python .dsh/tools/kb.py log-call --agent code-reviewer --task "<范围一句话>" --status ok|fail|blocked`。
   **完成判据**：`.dsh/knowledge/agent-calls/YYYY-MM-DD.jsonl` 出现对应一行。

## 质量闸门

- [ ] 范围来自 `git diff` 或用户清单，且写了未覆盖范围
- [ ] 每条问题有 `文件:行` 与证据片段
- [ ] 每条问题只有一个级别，级别定义可复述
- [ ] 结论与阻断数一致（有阻断 ≠ 可合并）
- [ ] 全程只读：未改文件、未跑 `checkout`/`install`/`rm` 等有副作用命令
- [ ] 秘钥原文未进入报告、日志、知识库
- [ ] 调用日志已写入

## 输出格式

```
结论：可合并 | 需修改 | 需重做（最大风险：…）
| 级别 | 位置 | 问题 | 证据 | 修复方向 | 阻断 |
|---|---|---|---|---|---|
| P1 | src/a.ts:42 | 未处理空数组 | `arr[0].id` | 先判空 | 是 |

待确认：…（需要什么信息）
未覆盖：…（本次没看的范围）
```

## 反面清单

- ❌ 通读全仓再挑毛病——只看变更面，否则噪声淹没真问题。
- ❌ 写「建议优化一下」却不给行号与证据——无法验证的建议等于没说。
- ❌ 有 P0 阻断仍给「可合并」——把风险转嫁给发布环节。
- ❌ 审查中直接改代码——审查者与修复者分离，改代码另开任务。
- ❌ 把秘钥原文贴进报告「证明」——发现即停，只报位置与类型。

## 用例

**成功用例**：用户说「审下这个 diff」。`git diff --stat` 显示 3 文件 120 行 → 主会话自查；发现 P1 一处未释放句柄、P2 两处重复分支；结论「需修改」，最大风险为句柄泄漏；`log-call` 记 `status: ok`。

**边界用例**：用户说「帮我把这个函数重写一下」。这是修改而非审查 → 不触发本 Skill，说明「审查只读，重写需另开任务并授权写业务文件」，避免审查者越权改代码。
