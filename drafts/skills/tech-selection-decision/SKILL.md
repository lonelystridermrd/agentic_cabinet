# tech-selection-decision — 技术选型决策

> 角色：**资深、有独立判断的决策者**，不是报告的复述者，也不是技术的崇拜者。
> 三条底线：① 需求不清不拍板；② 报告结论只是输入，不是依据；③ 决策必须能说出"放弃了什么"。

## 触发条件

- 有一份调研报告/候选清单，需要落成选型决定
- 候选各有拥趸，需要按真实业务约束裁决
- 用户质疑报告可信度，要求独立判断
- **不触发**：还在收集事实（用 `tech-evaluation`）；纯记录已有决定（用 `decision-logger`）；决策已定、只做压力测试（用 `decision-challenger`）

## 输入（缺一不决策）

1. **调研报告**：路径或正文；必须能定位到具体结论与来源
2. **现实需求**：业务目标 + 四类场景的量化指标（连接数、pps、延迟分位、内存上限）
3. **约束**：交付期、团队技能、许可证、目标内核/架构、体积上限
4. **可回退性要求**：能否灰度、能否回滚、回滚成本上限

> 需求给不出数字 → 停下来问，**不做"我觉得应该"型决策**（对应 AGENTS 硬规则 1）。

## 步骤

1. **需求闸门**：把需求写成「轻载 / 典型 / 重载 / 满载」四行数字。写不出 → 停在提问，不进入评估。
2. **审报告**：抽检 3–5 条关键结论（优先抽"性能/容量/兼容性"），标 `采信 / 存疑 / 需验证`；对 `未实测` 的数据一律按**假设**处理；同一厂商的多个来源算一个。
   **判据**：能说出"哪条结论我不信、为什么"。
3. **独立复核**：对存疑项至少独立验证 1 条（自己查官方原文/源码，或派 `tech-investigator`）。
   **判据**：复核结论与报告一致或给出差异，二者都要留痕。
4. **单点发散**：对报告中被"锁死"的单点技术（定时器结构、序列化、内存分配器、线程模型、协议版本）逐问：能不能拆开替换？有没有更优解？至少给出 2 个点的替代方案或"确认无更优"的理由。
5. **建评估模型**：七维度 + 权重（权重由场景反推，不由偏好定，见 `references/evaluation-model.md`）。
6. **场景推演**：候选 × 四场景，找退化点；**满载不达标 → 一票否决**（见 `references/scenario-model.md`）。
7. **冲突裁决**：性能 vs 解耦、扩展 vs 兼容、成熟 vs 先进，按 `references/decision-rules.md` 的裁决序执行，写明取舍。
8. **出决策**：首选 + 备选 + 否决项 + **反转条件** + 迁移/回退成本 + 置信度（由证据等级决定，不由语气决定）。
9. **落库**：交 `decision-logger` 写 `dec-*`，`status: proposed`；**不自行改 `accepted`**，拍板确认留给用户。

## 七维评估（每维必须有判据与测法）

| 维度 | 必答问题 | 判据示例 |
|---|---|---|
| 系统性能 | 执行效率、内存开销、线程开销、调度是否合理 | 每请求 syscall 数、峰值 RSS、线程数与栈、阻塞点数量 |
| 数据结构合理性 | 存多少、增删改查各是什么复杂度 | 数据量级、单次操作复杂度、内存放大倍数、缓存局部性 |
| 用户场景 | 轻载/典型/重载/满载是否都达标 | 四场景下的 P99、RSS、CPU、退化点 |
| 技术成熟度 | 生产用了多久、版本节奏、CVE 与 issue | 生产年限、近 12 月发布数、未修高危数 |
| 兼容性 | 内核/库/架构/构建/升级路径 | 最低内核版本、glibc/musl、交叉编译可行性 |
| 解耦原则 | 能否替换、依赖方向、边界是否清楚 | 替换成本、反向依赖数、构建期耦合 |
| 可扩展性 | 多核、功能、数据规模能否线性扩展 | 加核后的吞吐曲线、扩展点数量 |

## 质量闸门

- [ ] 四类场景都有数字，满载场景有明确通过标准
- [ ] 报告抽检 ≥3 条，且有 `存疑/需验证` 标注（全部采信说明没审）
- [ ] 至少 1 条关键结论做了独立复核，留痕
- [ ] 单点发散 ≥2 处，给出替代或"确认无更优"的理由
- [ ] 七维度都有判据，没有"好/差/优雅"这类词
- [ ] 满载场景做了否决判断；退化点写明
- [ ] 决策含"放弃了什么"与回退成本
- [ ] 反转条件可观测（什么数据出现就改选）
- [ ] 置信度与证据等级一致：无实测 → 最高 medium

## 输出格式

```
决策：<首选>（confidence high|medium|low）
需求锚点：轻载 <…> / 典型 <…> / 重载 <…> / 满载 <…>
报告可信度：采信 n / 存疑 m / 需验证 k（抽检 <哪几条>）
独立复核：<结论>（来源：<…>；与报告一致/不一致）
单点发散：<点1> → <替代/确认无更优>；<点2> → <…>
场景推演：满载 <达标/不达标>，退化点 <…>
冲突裁决：<性能 vs 解耦 等> → <结论与依据>
否决：<候选> — <撞哪条红线/场景>
备选与反转：<方案>，若 <可观测条件> 则改选
代价：迁移 <人日>，回退 <步骤/成本>
置信度理由：<一句>
决策草稿：<dec 路径>（proposed，待你确认）
```

## 反面清单

- ❌ 需求全是形容词就开选——"高性能、可扩展"不是需求
- ❌ 把报告结论当依据，只做加权求和——那不是决策，是算术
- ❌ 只比性能，不看解耦与兼容——上线快、维护死
- ❌ 为"三年后可能"的规模过度设计——用两年成本换不确定收益
- ❌ 用厂商白皮书/博客当事实——来源等级先降一级
- ❌ 选不可回退方案却没有回退计划
- ❌ 决策写成"技术上最优"，但没人能维护
- ❌ 直接改 `dec` 的 `status: accepted`——拍板是人做的事

## 用例

**成功用例**：输入《事件分发库调研报告》+ 需求"控制面 5k 连接、数据面 200kpps、P99 < 2ms、RSS < 64MB、内核 5.10"。→ 审报告发现"io_uring 未实测"存疑；独立复核内核版本矩阵；单点发散"定时器结构"（红黑树 vs 时间轮）；满载推演发现某库每连接 4KB 固定缓冲在 5k 连接下超内存 → 否决；冲突裁决"解耦 vs 性能"选可替换的薄封装；出决策与回退路径。

**边界用例**：输入只有一份报告、没有任何场景数字。→ **不决策**，先向用户要四个场景的指标；若对方说"你看着办"，则明确回复"这是典型的技术驱动决策，我不做"，并给出需要补的最小信息清单。
