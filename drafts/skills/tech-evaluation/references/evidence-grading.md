# 证据分级与置信度（A / B / C / D）

> 核心规则：**结论的置信度由证据等级决定，不由把握程度决定。**
> 拿不到可靠依据时，正确动作是降级并写明缺什么，不是把话说圆。

## 一、等级定义

| 等级 | 什么算 | 典型来源 | 能否单独支撑结论 |
|---|---|---|---|
| **A 一手规范/自测** | 标准、协议、官方文档（带版本）、源码本身、**自己的实测（六要素齐全）** | RFC / IEEE / 3GPP / ISO；厂商数据手册与 errata；内核文档与代码；库的官方 API 文档；自测脚本与原始输出 | 能（1 条即可，需交叉） |
| **B 可实现验证** | 权威项目的实际实现、他人可复现实测 | Linux/DPDK/FRR/OVS/systemd/glibc/musl 的源码用法；带方法的 benchmark；CVE 与 issue 记录 | 能（2 条独立） |
| **C 多方实践** | ≥3 个独立成熟项目采用同一做法 | 多项目源码/配置；维护者演讲、LWN 深度文章 | 能（3 条独立） |
| **D 线索** | 二手叙述、营销材料 | 博客、教程、公众号、AI 摘要、厂商白皮书里的"性能提升 10 倍" | **不能**，仅作检索线索 |

## 二、判定规则

1. 一条关键结论 = **≥1 个 A**，或 **≥2 个独立 B**，或 **≥3 个独立 C**。
2. **同源去重**：同一厂商/同一作者的多个页面算 1 个来源；同一 benchmark 被三家转载算 1 条。
3. **冲突处理**：A 与 D 冲突以 A 为准，并记录冲突与可能原因（版本差异、测试条件不同）。
4. **时效**：版本与日期必带；一手文档 >18 个月需确认是否有更新版本，否则降一级。
5. **基准测试必须**给：硬件、内核版本、编译选项、输入规模、测量方法、是否预热。缺任一 → 降为 C。
6. **自测优先**：同一指标有自测数据时以自测为准；引用他人 benchmark 必须带上述六要素，缺条件一律降级。
7. **推断必须标注**：用 `推断` 开头，并写出推断依据；不得混进结论段。

## 三、置信度映射

| 情况 | 置信度 |
|---|---|
| 关键结论有 A 级 + 跨来源交叉验证 + 无未解决冲突 | `high` |
| 关键结论仅 B/C，或 A 级存在但未交叉，或有关键项待 POC | `medium` |
| 仅 D 级、关键结论缺证据、来源互相矛盾未解决 | `low`（必须写"缺什么证据才能升级"） |

> 性能类结论默认最高 `medium`，除非有你自己的实测（POC）。

## 四、按问题类型取源

| 问题类型 | 首选 A 级 | 补充 B/C |
|---|---|---|
| 协议 / 标准行为 | RFC、IEEE、3GPP、ITU、ISO | 主流实现源码（Linux、FRR、wireshark dissector） |
| 内核 / 系统机制 | 内核文档 + 源码 + 主线 commit | LWN 深度文（C）、发行版实践（C） |
| 库 / 框架行为 | 官方文档（对应版本）+ 源码 | CHANGELOG、issue、下游项目用法 |
| 硬件 / 芯片 | 数据手册、勘误表 errata、厂商 SDK | 社区实测（C）、驱动源码（B） |
| 性能 / 容量 | 官方 benchmark（需方法） | 第三方可复现实测（B）、自己的 POC（A） |
| 生态 / 维护度 | 官方发布节奏、维护者结构 | issue 响应中位数、下游依赖数、发行版打包情况 |

## 五、常见伪证据（见到就降级）

- star 数 / 下载量 / "GitHub 趋势" —— 流行 ≠ 合适
- 厂商 benchmark（选择性输入、核数/包长未说明）
- "某大厂在用"（不说规模、不说怎么用、不说踩了什么坑）
- 博客复述官方文档 —— 是 D，不是 A
- AI 生成的对比表 —— D，且要回原文核对
- "社区都说好" —— 无代理指标的口碑不构成证据

## 六、缺证据时的标准写法

```
结论：暂无法判定（置信度 low）
缺：<具体缺什么，例如 io_uring 在 5.10 上的 P99 尾延迟数据>
升级路径：<谁/哪份文档/什么测试能给>
当前建议：<在证据补齐前，先按保守方案执行>
```
