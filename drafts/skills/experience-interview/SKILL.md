# experience-interview — 引导式经验梳理

> 目的不是"我问你答"，而是**把隐性判断变成可执行规则，并放到正确的容器里**。
> 单条踩坑用 `experience-capture`；本 Skill 处理"一个主题下的一整套手法"。

## 触发条件

- 用户主动说"梳理 / 访谈 / 沉淀我的做法"
- `profile.md` 或某个 reference 里有 TBD，且需要用户拍板
- 同一主题下已经积累 ≥3 条零散经验，需要归纳成手法
- **不触发**：单次 bug 复盘（用 `experience-capture`）；需求/规格讨论（用 `spec-writer`）

## 输入

- 主题（socket / 内存 / 数据结构 / 性能 / 并发 / 错误处理 / 日志 / 构建）
- 现状：`c-embedded-coding/references/profile.md` + 相关 reference + `kb.py search <主题>`
- 用户的时间预算（默认 30 分钟，一次只做一个主题）

## 步骤

1. **选题与定位**：确认主题，读现状，列出「已知 / 空白 / 冲突」三栏。空白项决定访谈重点。
2. **出题**：从 `references/question-bank.md` 取 8–10 题，按四类排序——① 你遇到过什么 → ② 你怎么判断 → ③ 你的默认值是什么 → ④ 什么情况下你会反着做。**一次最多问 5 题**，避免疲劳。
3. **回收与复述**：用户每答一条，立刻压成一句「条件 + 动作 + 反例」，回问"是这样吗？"。不复述就直接写文件，等于把猜测入库。
4. **判定去向**（见下表）：每条结论只进一个容器，不重复存。
5. **写回**：
   - 改已入库 Skill 的 `references/*.md` → 直接改，但**逐条**经用户确认；
   - 新建 Skill → 走 `.dsh/drafts/skills/`，不当场 promote；
   - 知识条目 → `experience-capture` / `decision-logger` / `pattern-spotter`；
   - 参数 → `profile.md`（并追加变更记录）。
6. **校验**：`python .dsh/tools/kb.py validate` + `python .dsh/tools/kb.py index`，零 error。
7. **收口**：输出「主题卡」，列出新增规则、改了哪些文件、还剩哪些空白。

## 去向判定表（本 Skill 的核心）

| 结论形态 | 容器 | 判据 |
|---|---|---|
| 每次写代码都要遵守的可执行规则 | Skill `references/style.md` / `safety.md` | 能写成"触发条件 + 动作"，能贴进检查清单 |
| 设计/选型手法（多方案取舍） | Skill `references/*.md`（playbook） | 需要看约束才能决定，不是单条 if |
| 具体踩坑事件（有症状/根因/修法） | `exp-*` | 能说出"哪次、什么现象、根因是什么" |
| 跨主题反复出现的规律 | `pat-*` | 在 ≥3 条经验里出现同一模式 |
| 一次性的技术取舍 | `dec-*` | 有备选方案和代价，且以后可能被质疑 |
| 只是一个默认数字/开关 | `profile.md` | 改它只影响参数，不影响流程 |
| 只是背景信息/事实 | 不进库（写进对话或项目文档） | 下次不会因此改变动作 |

**冲突处理**：同一件事既有 Skill 规则又有 exp-* 条目时，Skill 只留一行规则 + 指向 exp ID；详细因果留在 exp。

## 质量闸门

- [ ] 每条规则都有「反例」（写不出反例说明规则太宽）
- [ ] 没有"注意 / 小心 / 尽量"这类不可判定的词
- [ ] 每条都经用户口头确认（复述过一遍）
- [ ] 去向判定逐条有理由（没有"看着像就放这儿"）
- [ ] 一次只处理一个主题，未跨主题混写
- [ ] `kb.py validate` 零 error

## 输出格式

```
主题：<socket / 内存 / ...>    用时：<n> 分钟
新增规则：<n> 条
  - <规则一句话> → <落到哪个文件/条目 ID>
更新文件：<路径列表>
转入知识库：<exp-*/dec-*/pat-* 列表，没有写"无">
仍空白：<下次要问的 2–3 个问题>
待确认：<需要用户拍板的 1–2 个点>
```

## 反面清单

- ❌ 一次问 20 个问题（用户答到第 8 个就开始敷衍，回收质量断崖）
- ❌ 把用户的话原样贴进 Skill（Skill 要的是可执行规则，不是访谈记录）
- ❌ 没复述就写文件（等于把模型的理解当成用户的经验）
- ❌ 同一结论既写 Skill 又写 exp-*（两处必然漂移）
- ❌ 新建 Skill 绕过 drafts 直接写 `.dsh/skills/`（G3 闸门）
- ❌ 把公司代码/内部域名带进知识库（G5）

## 用例

**成功用例**：用户说"梳理一下我在 socket 上的做法"。→ 读 `socket.md` 与 `profile.md`，发现"读超时用 poll 还是 SO_RCVTIMEO"是空白；问 5 题（遇到过什么超时问题 / 怎么判断连接死了 / 默认超时多少 / 什么时候反过来 / 怎么观测）；回收成 4 条规则，3 条进 `socket.md`，1 条参数进 `profile.md`；输出主题卡。

**边界用例**：用户说"上次那个 `recv` 返回 0 的坑记一下"。→ 不触发本 Skill（这是单条事件），直接走 `experience-capture`；若该坑已在 `pitfalls.md` 的 #7，则把标记从 `通识` 改成 `我踩过` 并生成 `exp-*`，不新增 Skill 规则。
