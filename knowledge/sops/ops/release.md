# 发布 SOP

## 适用与不适用

- 适用：有明确版本边界的一批变更。
- 不适用：开发中预览、热修（热修走 `incident-responder` 的紧急路径，事后补本文档）。

## 步骤

1. **收齐变更** — `release-manager`（派发）
   - `git log <last-tag>..HEAD` 取提交，归为 feat/fix/refactor/docs
   - 完成判据：无未归类提交
2. **定版本号** — 自己
   - 破坏性 → major；新功能 → minor；修复 → patch
   - 完成判据：版本号能由变更清单反推出来
3. **写 changelog** — 自己
   - 按「用户可见变化」组织，不按提交顺序
   - 完成判据：每条能回答「用户会感知到什么」
4. **发布检查** — 自己（或 `release-manager`）
   - 测试通过 / 配置项齐全 / 回滚步骤可执行 / 公告草稿
   - 完成判据：四项全绿，回滚命令已实际演练过一次
5. **执行发布** — 用户（Agent 不执行对外发布）
   - 完成判据：版本已上线并有健康检查证据
6. **记录** — `decision-logger`（若本次发布含取舍）/ daily-log
   - 完成判据：发布决策与结果在同一处可追溯

## 检查点

- [ ] 变更清单完整，无未归类提交
- [ ] 版本号与变更性质匹配
- [ ] changelog 面向用户可读
- [ ] 回滚步骤经过演练（不是只写在文档里）
- [ ] 秘钥与内部地址未进入 changelog
- [ ] 发布动作由人执行，Agent 只准备材料
